# DRAFT-LLM: Dataset Readiness Assessment for Training

**Version:** 1.0  
**Status:** Reference implementation  
**License:** Copyleft

DRAFT-LLM is a structured, reproducible framework for auditing high-dimensional biological datasets and evaluating predictive models with optional large language model assistance.

It extends the Dataset Readiness Assessment for Training (DRAFT) protocol through:

- structured study and dataset documentation;
- modality-specific descriptive statistics;
- configurable LLM behavior and governance;
- personalized audit instructions;
- executable generalization, equity, and stability assessments; and
- a rule-based baseline for evaluating whether an LLM adds value.

DRAFT-LLM can support tabular, genomic, imaging, textual, time-series, multimodal, and other high-dimensional biological data.

---

## Framework Overview

DRAFT-LLM separates the workflow into four **Support Protocols** and three **Basic Protocols**.

The Support Protocols progressively transform study information and empirical dataset properties into a validated, study-specific instruction bundle. The Basic Protocols use that bundle to execute the principal audits.

```text
Study objectives and data sources
              │
              ▼
SP1 — Study Intake and Dataset Card
              │
              ▼
SP2 — Dataset Statistics and Structure Card
              │
              ▼
SP3 — LLM Configuration
              │
              ▼
SP4 — Personalized Audit Instruction Bundle
              │
       ┌──────┴──────┐
       │             │
       ▼             ▼             ▼
BP1 — Generalization  BP2 — Equity  BP3 — Stability
```

The Basic Protocols are thin, reusable execution patterns. Their concrete behavior is determined by the cards, statistics, governance constraints, resource limits, and instructions generated by the Support Protocols.

## Support Protocols

The root-level Support Protocol directories contain reusable infrastructure that can be adapted to different biological studies and data modalities.

### Support Protocol 1 — Study Intake and Dataset Card Construction

```text
support-protocol-1/
```

#### Purpose

Support Protocol 1 documents the scientific objective, prediction task, dataset structure, user requirements, governance conditions, and computational constraints.

It produces a machine-readable **Dataset Card** that serves as the authoritative study specification for all downstream protocols.

#### What SP1 records

SP1 captures:

- the primary scientific question;
- intended model use;
- prediction task type;
- primary and secondary outcomes;
- inclusion and exclusion criteria;
- analysis time origin;
- cohort restrictions;
- data sources and modalities;
- table and file names;
- sample and feature counts;
- linkage keys;
- processing levels;
- variable descriptions and data types;
- canonical variable roles;
- sensitive attributes;
- grouping, cluster, batch, site, and time variables;
- prohibited predictors, including post-outcome information;
- user expertise and preferred explanation style;
- governance and risk constraints; and
- available computational resources.

Canonical variable roles may include:

- identifier;
- outcome;
- predictor;
- sensitive attribute;
- technical or batch variable;
- time variable; and
- grouping or cluster variable.

#### How to use SP1

1. Document the study objective and intended model use.
2. Define the analysis cohort and time origin.
3. inventory all data sources and modalities.
4. Enumerate variables and assign canonical roles.
5. Identify outcomes, sensitive attributes, grouping variables, and prohibited predictors.
6. Record governance, privacy, user, and resource requirements.
7. Validate the completed card against the SP1 JSON Schema.
8. Review the generated card before proceeding to SP2.

#### Primary output

```text
dataset_card.json
```

This file is used by SP2 to guide statistical characterization, by SP3 to establish study and governance context, and by SP4 to generate audit-specific instructions.

### Support Protocol 2 — Dataset Structure and Advanced Summary Statistics

```text
support-protocol-2/
```

#### Purpose

Support Protocol 2 characterizes the empirical properties of the dataset described in SP1.

It produces a standardized **Statistics Card** containing global, subgroup, structural, and modality-specific summaries suitable for downstream analyses and LLM context.

#### What SP2 evaluates

SP2 may calculate or document:

- global sample and feature counts;
- outcome distributions;
- class imbalance;
- missingness patterns;
- subgroup sample sizes;
- subgroup outcome distributions;
- dependence and clustering;
- site, batch, and temporal structure;
- heterogeneity;
- dimensionality;
- potential leakage indicators;
- data sparsity;
- modality-specific quality indicators; and
- limitations affecting the planned audits.

Supported statistics may differ by modality:

| Modality | Representative summaries |
|---|---|
| Tabular | Missingness, distributions, imbalance, correlations and subgroup counts |
| Imaging | Dimensions, channels, intensity distributions and image-quality summaries |
| Text | Document lengths, vocabulary summaries and missing-text patterns |
| Time series | Sequence lengths, sampling intervals, temporal gaps and irregularity |
| Genomic or other high-dimensional data | Feature counts, sparsity, variability and dimensional structure |
| Graph data | Nodes, edges, degree distributions, components and connectivity |

#### How to use SP2

1. Load the validated SP1 Dataset Card.
2. Select the notebook or script corresponding to each data modality.
3. Compute global and subgroup statistics.
4. Evaluate outcome imbalance, missingness, dependence, and heterogeneity.
5. Record relevant site, batch, grouping, and temporal structures.
6. Review warnings and modality-specific diagnostics.
7. Consolidate the results into a Statistics Card.
8. Validate the card before using it in SP3.

SP2 should describe observed properties without overstating their scientific or clinical meaning. Statistical warnings require human interpretation.

#### Primary output

```text
statistics_card.json
```

The Statistics Card provides the empirical evidence used by SP3 to derive data-risk flags and by SP4 to personalize the three audit designs.

### Support Protocol 3 — LLM Configuration Using Structured Form Responses

```text
support-protocol-3/
```

#### Purpose

Support Protocol 3 combines the study intent documented in SP1 with the empirical evidence generated by SP2.

It produces a validated **LLM Configuration** that defines how DRAFT-LLM should interact with the researcher and what methodological, governance, and resource constraints it must follow.

SP3 functions as a configuration and policy layer. It does not train or fine-tune an LLM.

#### What SP3 configures

The configuration includes:

- study goal and analysis type;
- intended use and risk level;
- user expertise;
- interaction and explanation style;
- preferred code style;
- sensitive attributes;
- permitted uses;
- forbidden operations;
- interpretability requirements;
- privacy and governance conditions;
- compute budget;
- allowed software libraries;
- environment restrictions;
- data-driven risk flags;
- behavior cues;
- base system prompts; and
- reusable user prompt templates.

Representative data-risk fields include:

```text
imbalance_flag
must_discuss_imbalance
missingness_flag
must_address_missingness
heterogeneity_flag
```

These flags should agree with the empirical properties reported in the SP2 Statistics Card.

#### How to use SP3

1. Provide the validated SP1 Dataset Card.
2. Provide the validated SP2 Statistics Card.
3. Complete or adapt the SP3 configuration form.
4. Set user-interaction, governance, safety, and resource requirements.
5. Generate the LLM Configuration.
6. Review consistency checks between SP1 and SP2.
7. Verify that the derived risk flags reflect the observed data.
8. Review the generated system and user prompt templates.
9. Adjust thresholds or source artifacts if inconsistencies are found.
10. Regenerate and validate the configuration before proceeding to SP4.

Changes to prompt wording should be made in the human-readable Markdown templates and then compiled again. Directly editing only the generated prompt strings can create inconsistencies between source templates and final artifacts.

#### Primary output

```text
llm_config.json
```

This file provides the study profile, user profile, governance rules, resource limits, data-risk flags, and prompt configuration required by SP4.

---

### Support Protocol 4 — Personalized Instructions for DRAFT Audits

```text
support-protocol-4/
```

#### Purpose

Support Protocol 4 is the final assembly stage of the support layer.

It combines the outputs of SP1–SP3 with reusable audit templates to generate a study-specific **Audit Instruction Bundle** for the generalization, equity, and stability Basic Protocols.

The bundle determines how each audit should be designed while preserving the study context, empirical risk indicators, governance requirements, and resource limits established upstream.

#### What SP4 generates

For each enabled audit, SP4 may generate:

- an audit objective;
- a study-specific system prompt;
- task-specific user prompt templates;
- an audit profile;
- recommended evaluation strategies;
- candidate metrics;
- subgroup or grouping requirements;
- uncertainty-reporting requirements;
- governance restrictions;
- resource-aware constraints; and
- source-version and generation metadata.

The instruction bundle can contain sections for:

```text
generalization
equity
stability
```

#### How to use SP4

1. Provide the validated SP1 Dataset Card.
2. Provide the validated SP2 Statistics Card.
3. Provide the validated SP3 LLM Configuration.
4. Select the audits to enable.
5. Configure user priorities and audit focus, when applicable.
6. Build the instruction bundle using the reusable audit templates.
7. Review the extracted context and audit profiles.
8. Inspect all generated prompts for unresolved placeholders.
9. Apply governance filters and consistency checks.
10. Validate the final bundle against its JSON Schema.
11. Freeze and version the bundle before executing the Basic Protocols.

SP4 generates instructions; it does not execute statistical analyses or guarantee that generated recommendations are scientifically appropriate.

#### Primary output

```text
instruction_bundle.json
```

This bundle is the direct instruction source for the three Basic Protocols.

## Basic Protocols

### Basic Protocol 1 — Generalization Audit

The generalization audit evaluates whether model performance extends beyond the observations used for model development.

The audit design should be derived from the SP1–SP4 artifacts and may include:

- random cross-validation;
- stratified cross-validation;
- grouped cross-validation;
- nested cross-validation;
- site-aware evaluation;
- batch-aware evaluation;
- temporal validation;
- external validation;
- out-of-distribution analysis;
- leakage checks;
- discrimination metrics;
- calibration metrics; and
- sensitivity analyses using alternative data splits.

The audit must account for dependence, class imbalance, limited sample size, heterogeneity, and the intended model use.

---

### Basic Protocol 2 — Equity Audit

The equity audit evaluates whether aggregate model performance hides failures or disparities across authorized sensitive groups.

Using SP4 prompts, the researcher first defines an equity evaluation strategy specifying:

- subgroups and intersections to report;
- subgroup-appropriate metrics;
- aggregation and disaggregation rules;
- minimum subgroup-size requirements;
- uncertainty-reporting methods;
- thresholds of concern;
- assumptions about group labels;
- assumptions about group stability; and
- assumptions about outcome-label comparability.

Representative metrics include:

- sensitivity;
- specificity;
- positive and negative predictive values;
- calibration;
- error rates;
- performance gaps; and
- performance ratios.

The selected strategy is then implemented, with subgroup-level outputs such as counts, confusion matrices, calibration summaries, and uncertainty estimates retained for review.

Sensitive attributes must only be used when permitted by the study governance configuration.

---

### Basic Protocol 3 — Stability Audit

The stability audit evaluates whether model performance, selected predictors, salient elements, and interpretations remain consistent across relevant perturbations.

Possible perturbations include:

- repeated resampling;
- alternative training and validation splits;
- random-seed changes;
- model specifications;
- feature-selection procedures;
- site or batch exclusions;
- subgroup restrictions;
- missing-data strategies; and
- modality-specific preprocessing choices.

The granularity of salient elements—for example, feature, token, span, document, tool, or reasoning step—and the number of tracked elements should be determined from SP2 and constrained by SP3.

These settings must remain fixed during SP4 and audit execution. Otherwise, apparent instability may reflect changing extraction settings rather than genuine changes in model behavior or evidence use.

## Rule-Based Baseline

DRAFT-LLM includes a rule-based baseline based on JSON-Schema-validated templates.

The baseline maps the Dataset Card, Statistics Card, and LLM Configuration directly into executable Basic Protocol instructions without requiring an LLM.

This comparison helps evaluate whether the LLM component is necessary.

Rule-based templates can consistently parameterize standard audits. The LLM layer may provide additional value when adapting evaluation strategies to edge cases such as:

- extreme class imbalance;
- small or sparse subgroups;
- complex multimodal intersections;
- unusual dependence structures;
- competing governance requirements; and
- restrictive computational environments.

These potential advantages must be tested rather than assumed. LLM-generated instructions should be compared with the deterministic baseline for validity, consistency, reproducibility, and resource use.

## End-to-End Workflow

### Step 1 — Define the study

Use SP1 to document:

- the scientific question;
- prediction task;
- intended use;
- analysis cohort;
- data sources;
- variable roles;
- sensitive attributes; and
- governance constraints.

Output:

```text
dataset_card.json
```

### Step 2 — Characterize the dataset

Use SP2 to calculate:

- global statistics;
- subgroup statistics;
- outcome distributions;
- missingness;
- imbalance;
- dependence;
- heterogeneity; and
- modality-specific summaries.

Output:

```text
statistics_card.json
```

### Step 3 — Configure DRAFT-LLM

Use SP3 to define:

- user preferences;
- governance rules;
- forbidden operations;
- resource limits;
- data-risk flags; and
- prompt behavior.

Output:

```text
llm_config.json
```

### Step 4 — Generate audit instructions

Use SP4 to combine the previous artifacts with reusable audit templates.

Output:

```text
instruction_bundle.json
```

### Step 5 — Execute the Basic Protocols

Use the frozen SP1–SP4 artifacts to run:

```text
bp1_generalization.ipynb
bp2_equity.ipynb
bp3_stability.ipynb
```

### Step 6 — Review and preserve results

Preserve:

- input cards;
- configuration files;
- instruction bundles;
- prompts;
- audit specifications;
- source-code versions;
- package versions;
- random seeds;
- intermediate outputs;
- warnings;
- validation reports; and
- final interpretations.

When study goals, data, statistics, governance constraints, or templates change, regenerate the affected SP1–SP4 artifacts and rerun the Basic Protocols.

## Validation and Reproducibility

All generated JSON artifacts should be validated against their corresponding schemas.

Before executing an audit:

1. confirm that the SP1 study specification is accurate;
2. verify the SP2 statistical summaries;
3. check that SP3 risk flags agree with the observed data;
4. review SP3 governance and resource constraints;
5. inspect SP4 prompts and profiles;
6. confirm that no template placeholders remain unresolved;
7. record the versions of SP1–SP4;
8. record the Git commit and software environment; and
9. freeze the artifacts used for the audit.

Audit conclusions are conditional on the exact versions of SP1–SP4 used. Earlier conclusions should not be reused after material changes to study goals, data, statistics, governance requirements, or audit settings.

## Responsible LLM Use

DRAFT-LLM treats the LLM as a research assistant and intellectual sparring partner rather than an autonomous decision-maker.

Users must:

- review all generated recommendations;
- verify proposed statistical methods;
- reject unsupported claims;
- avoid sending identifiable participant data to external services;
- enforce governance requirements outside the prompt;
- validate generated code before execution;
- use isolated execution environments;
- document manual changes; and
- retain qualified scientific oversight.

Prompt instructions are not security controls. Governance rules must also be enforced through technical, administrative, and organizational safeguards.

---

## Limitations

- DRAFT-LLM does not determine clinical readiness.
- It does not replace statistical, ethical, legal, regulatory, or domain review.
- Audit quality depends on the completeness and accuracy of upstream artifacts.
- JSON Schema validation verifies structure but not scientific correctness.
- Summary statistics may omit relevant dataset properties.
- Small subgroups may prevent reliable equity analysis.
- Stability does not establish causality or biological validity.
- LLM outputs may contain errors, unsupported claims, or inappropriate recommendations.
- Rule-based and LLM-generated instructions both require human review.
- Version 1.0 is a reference implementation rather than a validated medical device.
